# Boundary: Reading view

The document view of an agent terminal: the conversation as a timeline, the composer that types into the CLI, the
terminal popup every confirmation, question, menu and slash command is answered in (no option cards), the result card of
the latest round, and the switch between reading and the raw terminal.

## Owns
- `src/features/reading/**`

## Interface
- `ReadingView` (`src/features/reading/ReadingView.tsx`) — the reading view of one agent terminal; the file also exports Markdown, the renderer the review card and skill pane reuse
- `ModeSwitch` (`src/features/reading/ModeSwitch.tsx`) — the title bar's reading / terminal switch for the terminal in use
- `setReading` (`src/features/reading/reading-mode.ts`) — reading or raw terminal per terminal; the file also exports readingShown, syncReading and useTerminalChoice
- `hasCliInput` (`src/features/reading/cli-panel.ts`) — what the CLI's input line holds; the file also exports isAtPrompt, cliInputDraft and isCliIdle
- `sameMessage` (`src/features/reading/pending-prompts.ts`) — whether a sent message is the one still in the CLI input
- `lastRound` (`src/features/reading/result-round.ts`) — the latest round of a conversation; the file also exports CHECKS, changeLabel and `unconfirmed` (a step its source could not confirm is drawn as a grey question and is no pass in the result's checks)
- `ConversationFeed` (`src/features/reading/ConversationFeed.tsx`) — grouped read-only messages and tool steps, independent of composer and terminal state; the reading view, the sub-agent split and a session without a terminal render with it; the file also exports `ConversationDecorations`, the slots the interactive reader fills; user-side messages use main-owned sender metadata (owner or planner), with an unknown planner shown neutrally.
- `TimelineStep` (`src/features/reading/feed-parts.ts`) — the parts around a feed that a view without a terminal draws the way the reading view does: timeline steps, pending messages, the working line, the result row, picture chips (and `pastedPicture`, the picture a paste carries), the scroll that follows the newest step and the message box's helpers: `useComposerHistory` (↑↓ through what was sent), `useCommandPalette` with `commandList` and `composerAria` (the "/" list), `useMentions` and `MentionPalette` ("@" files)
- `QuoteChip` (`src/features/reading/ReadingQuote.tsx`) — the one quote chip above the composer; a message's right-click menu 引用 / 复制 is `MessageCard` (`MessageMenu.tsx`, rules in `message-menu.ts`); `message-quote.ts` exports quoteExcerpt, withQuote and splitQuote; ConversationFeed offers the menu only when its parent supplies quote decorations (the sub-agent split supplies none)
- `FileCards` (`src/features/reading/FileCards.tsx`) — the preview cards of the files a reply names; image cards deduplicate the main-resolved path within this group only, including an optional already-shown generated image; the file also exports previewable
- `replyFiles` (`src/features/reading/reply-files.ts`) — the local pictures, pages and videos a reply names

## Invariants

- A live composer stays editable during work, dialogs and unknown output; versioned host CLI state controls status, and a newer observed state from the same PTY may supplement it; positive waiting evidence opens the terminal only in the visible selected split, once per width-independent prompt episode, and messages queue FIFO until input returns, while an idle frame clears stale waiting immediately and opening while the owner edits never focuses xterm. A busy CLI admits a message on a completed parse, even with more output queued; unthrottled parse notifications drive admission and bounded waits for pending output to drain, while UI notifications coalesce over 100 ms. Each staged attempt belongs to a terminal epoch and parse counter; row revisions change only with the rows. Paste, Enter, Ctrl+U and Enter retries require pending output to be zero and recheck identity, input and host waiting. The composer pastes its own text before Enter when Claude shows a prompt suggestion. Before Enter, a drain failure keeps already pasted text uncertain and never re-pastes it. After Enter, a timeout or dialog only stops retries: the pending echo remains available for a late receipt or the undelivered UI. An interrupted outbox attempt may finish a confirmed paste with one Enter only from the same PTY epoch and a newer completed parse of its exact unsent words; an empty input permits one retry when the paste was never attempted or IPC rejected it, and further retries when each receiver refusal proves no write. An ordinary held message still drains while its project is hidden; only a held command waits for visibility. An in-flight or accepted paste without that input stays uncertain, and receipt ownership survives recovery. Timestamped queue or user receipts pair one-to-one with earlier unacknowledged echoes before uncertain outbox entries, even while delivery is blocked; untimestamped history, older identical records and cancelled queues cannot clear them. Receipt ownership survives later snapshots and remounts. Automatic sends show an echo only after the paste succeeds or when submitting their already pasted words. An in-flight send says it is sending. Whole sentences selected by terminal reason code explain why an outbox waits, and queued wording requires a CLI receipt. Keys that act at once (Shift+Tab, Esc, Stop) wait for a parsed frame with no dialog.
