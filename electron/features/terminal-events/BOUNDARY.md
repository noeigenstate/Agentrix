# Boundary: Terminal events

How a terminal's CLI reports to main: the Claude Code hook events (over HTTP to main's loopback hook server, or as commands through the event pipe) and transcript, and the Codex and Claude turn snapshots, turned into the terminal's CLI state, lights and completion alert; which hook channel a terminal uses and the settings its claude wrapper passes; and the bootstrap file a terminal's hooks and the dispatch helper read to reach main.

## Owns
- `electron/features/terminal-events/**`

## Interface
- `createClaudeActivity` (`electron/features/terminal-events/claude-activity.cjs`) — followClaude, followClaudeSession, publishCliState, applyActivity, claudeActivity and claudeHook over the app shell's deps, read on every call; main hands it every agent-activity event and every turn snapshot, and the hook server's ingest hands claudeHook every HTTP hook event
- `createSessionMachine` (`electron/features/terminal-events/session-machine.cjs`) — a Claude terminal's session machine (C-4): `reduce(state, signal) → { state, effects }`, pure, over hooks, transcript records, screen facts and the settled read after a Stop; phases starting, ready, working, stopping, exited; effects `subagent` (C-15) and `completion`; `cliFields` is its part of the published CliState (phase, turn, queue, background, open)
- `writeBootstrap` (`electron/features/terminal-events/bootstrap-file.cjs`) — the one writer of a terminal's or native session's bootstrap file (session key, event pipe, control channel, and a terminal's hooks), readable only by its owner
- `createHookServer` (`electron/features/terminal-events/hook-server.cjs`) — `(ingest, { limit }) → { port, close }`: Claude Code's HTTP hooks, POST `/h/<terminalId>/<EventName>` with `X-Agentrix-Key` on 127.0.0.1, bodies up to 4 MB
- `createHookIngest` (`electron/features/terminal-events/hook-ingest.cjs`) — `({ keyOf, deliver, now }) → { admit, take, abort, stats }`: requests become C-2 TerminalHookEvents `{ seq, terminalId, event, at, sessionId, transcriptPath, promptId, toolUseId, agentId, payload }`; stats() counts received, refused (path, terminal, key), oversize, unparsable, failed and aborted, for pipeline health
- `terminalHooks` (`electron/features/terminal-events/hook-channel.cjs`) — a local terminal's `hooks` (C-2): `{ url, port, key, channel, fallback, channelReason, settings: { http, fallback } }`, the one generator of the --settings every claude wrapper passes; downgradeHooks applies a wrapper's hook-channel report

## Invariants
- A Claude terminal's state comes from one session machine fed by its hooks, transcript reads and screen facts, and its phase only moves forward: a repeat, a hook reordered within its prompt, a transcript record read after its turn ended, an older prompt's late Stop, or a signal of an old epoch (another Claude session, an earlier launch, another PTY session's frame) never moves it back or clears newer attention; under command-async a hook of a prompt whose Stop was applied, or a permission notice older than a tool hook of its prompt, changes nothing; the screen only ends a turn Esc interrupted (its working line seen, then gone with the input shown and no dialog) and never acts for the owner; test: `tests/main-cli-state.test.cjs` › "under command-async a permission notice older than a tool hook of its prompt raises no waiting light, and a sync dialog hook still does"
- A completion needs the machine's completion effect: the newest prompt's Stop, an empty queue and no background work as CompletionWork reports it, at most once per owner round; progress, a repeated Stop, a local command, idle and background callbacks and screen facts never arm or rearm it, and a StopFailure (the turn ended in an API error) ends the round as interrupted, never completed, so it disarms the alert and never raises it (the HTTP channel and the command fallback's stop-failed kind alike); a screen-ended turn on a command channel leaves the round to its trailing Stop — AGENTS.md: completion notifications are never rearmed by idle or background callbacks — test: `tests/terminal-session-machine.test.cjs` › "a completion effect needs Stop, an empty queue and no background work"; test: `tests/terminal-session-machine.test.cjs` › "on a command hook channel the screen turns the light idle and a trailing Stop still completes the round"; test: `tests/main-cli-state.test.cjs` › "local command completion clears attention, while progress and repeated Stop never rearm completion"; test: `tests/main-cli-state.test.cjs` › "a StopFailure ends the round without rearming completion when the turn failed"; test: `tests/main-cli-state.test.cjs` › "a StopFailure on the command channel ends the round as interrupted without rearming completion"
- main.cjs defines none of this module's functions and writes no bootstrap file itself; it only wires the module — main regrowing the carved region would bring back the bottleneck every round edits — test: `tests/main-carve-out.test.cjs` › "main.cjs only wires the terminal activity, bootstrap, switch host, host inputs and dispatch intake modules"
- Status hooks never add model context: every HTTP hook is answered exactly `{}`, built only by hook-response.cjs, nothing else on the hook path writes context, a system message, `continue` or a decision, and the one settings generator gives HTTP hooks for every event but SessionStart (the one command that delivers skills), or the declared command fallback — a Stop answered with context makes Claude go on by itself — test: `tests/terminal-hook-silence.test.cjs` › "every state hook answers exactly {} and only an owner token can produce a PermissionRequest decision"; test: `tests/terminal-events-guards.test.cjs` › "additionalContext, systemMessage, displayContent, continue and decision:block appear only in hook-response.cjs"; test: `tests/terminal-events-guards.test.cjs` › "the settings generators emit only http hooks but SessionStart, or the declared command fallback"
- The CLI never waits on Agentrix: the reply is written before the event is ingested, a request without a live terminal's key is answered 404 and counted, and an event over 4 MB is still answered and taken from its URL with no payload, counted as oversize — every hook holds a turn until it is answered — test: `tests/terminal-hook-server.test.cjs` › "the reply is written before ingest runs: an ingest that never settles never delays it"; test: `tests/terminal-hook-server.test.cjs` › "an event over 4 MB is answered {} and still taken from its URL, counted as oversize"
- A terminal keeps command hooks, its status hooks async only on Windows (K0b items 3 and 7) and its dialog hooks always synchronous, and says why, when HTTPS_PROXY or HTTP_PROXY (either case; ALL_PROXY never reaches the hook client) in its environment or Claude Code's settings env is not exempted for 127.0.0.1 by every NO_PROXY and no_proxy set; the channel field follows each claude launch: a wrapper's hook-channel report holds for the launch it precedes (paired by shell event sequence, as the two land on separate pipe connections in either order), and a launch with none reads the terminal's own channel again — in doubt, command hooks; the PowerShell, Bash and zsh wrappers apply the same rule to their live environment and only ever fall back; Agentrix never adds a NO_PROXY entry — the hook client sends through such a proxy and the turn's reports would be lost — test: `tests/terminal-events-guards.test.cjs` › "command-async runs asynchronously only what K0b proved, besides the progress hooks every command channel runs so, and never a dialog hook"; test: `tests/terminal-hook-channel.test.cjs` › "with a proxy and no loopback NO_PROXY entry the terminal keeps command hooks in PowerShell, bash and zsh alike, and says why"; test: `tests/terminal-hook-channel.test.cjs` › "when NO_PROXY and no_proxy differ, 127.0.0.1 is exempt only if both exempt it"; test: `tests/terminal-hook-channel.test.cjs` › "Agentrix adds no NO_PROXY entry anywhere but system-proxy.cjs's adoption, which is unchanged"; test: `tests/terminal-hook-channel.test.cjs` › "the channel field follows each launch, so a launch after a downgrade without a proxy reads http"; test: `tests/terminal-hook-channel.test.cjs` › "a report and its launch pair by sequence, since they land on separate pipe connections in either order"

- Smokes, probes and stand-ins send a hook the way the terminal it targets would: through one hook client that reads the terminal's own channel (HTTP to its key and URL, otherwise the hook script), whose fake receiver answers as hook-server.cjs does — a smoke on the old channel would pass while the real one is broken — test: `tests/claude-hook-client.test.cjs` › "an HTTP terminal gets a keyed POST per event and the answer is 200 with {}"; test: `tests/claude-hook-client.test.cjs` › "typed into a terminal, a hook picks the channel from the terminal's own session and quotes the JSON"

## Not ours
- Spawning the PTY, the session records and restore plans — main.cjs (app shell)
- Round completion, prompt queues and the completion notification — Completion
- Reading the transcript records into the conversation, actions and usage — Activity pane and the readers main passes in
- The event pipe server and the hooks' own scripts — electron/events.cjs and integration/
- A proxy in Claude Code's settings env that appears after a terminal started (a project the user moves into) — a known limit: hook-channel.cjs reads the settings env once, at terminal start, and treats it as honoured by the hook client; the wrappers re-check only their live environment
